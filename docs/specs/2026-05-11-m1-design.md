# Convoy M1 — Design Spec

**Date:** 2026-05-11
**Milestone:** M1 (foundational coordination layer)
**Status:** Draft — pending review

---

## 1. Overview

Convoy is a local coordination layer for AI coding agents. M1 delivers the
foundational protocol and storage so that two or more **Claude Code** sessions
running in the same project (or in different worktrees of the same project)
can:

- Discover each other automatically
- See what each peer is working on
- Send each other messages
- Claim files to prevent concurrent edits
- Wait for a peer to finish before proceeding

M2 extends adapters to Codex CLI and Gemini CLI. M3 adds a multi-project web
dashboard and communication analytics. **This spec covers M1 only.**

---

## 2. Goals & Non-Goals

### In scope (M1)

- Local daemon process (single host, single user)
- Per-project SQLite storage with human-readable mirror exports
- MCP server exposing coordination tools to the Claude Code model
- Hooks for auto-registration, heartbeat updates, branch tracking, deregistration
- CLI for inspection and lifecycle management (`list`, `status`, `show`,
  `export`, `finish`, `forget`, `doctor`, `gc`)
- Async mailbox with auto-inject into the model's context
- File-claim locks with TTL
- Cooperative `wait_for` semantics
- Rate limiting

### Out of scope (deferred to M2/M3)

- Codex / Gemini / Cursor adapters
- Web dashboard or TUI
- Cross-host coordination
- Communication analytics
- Authentication beyond UNIX file permissions
- Encryption at rest

## 3. Background — what already exists, what gap we fill

| Existing tool | What it does | Gap |
|---|---|---|
| Claude Code Agent Teams (experimental) | Shared task list, P2P mailbox, file locks within one Claude team | Within-team only; not across independently-launched sessions |
| `ccmanager` | Session launcher across many CLIs | Launches but does not coordinate runtime conflicts |
| `claude-mem` | Persistent context across sessions | Memory only; no live communication or locking |
| `tick-md` | TICK.md file as coordination point | Plain markdown; no atomic claim semantics |
| `MCP Agent Mail` | Mail-based MCP coordination | Mail only; no locks, heartbeat, or per-project isolation |
| `Overstory`, `Citadel`, `ccswarm` | One controller spawns workers in worktrees | Top-down orchestration; not peer-to-peer between independent user-launched sessions |

**Convoy's gap:** peer-to-peer coordination between **independently launched**
Claude Code sessions (whoever opens a terminal and runs `claude` joins the
convoy), with structural per-project storage that is transparent and
user-removable.

## 4. Architecture

### 4.1 Component diagram

```
+--------------------------------------------------------------+
|                        User's machine                         |
|                                                               |
|   Claude Code session A          Claude Code session B        |
|   (terminal 1, branch X)         (terminal 2, branch Y)       |
|       |     |                        |     |                  |
|       |     +-- hooks ----+          |     +-- hooks ----+    |
|       |                   |          |                   |    |
|       +-- MCP stdio --+   |          +-- MCP stdio --+   |    |
|                       v   v                          v   v    |
|                  +--------------------------------------+     |
|                  |        convoy mcp  (stdio)           |     |
|                  |   one instance spawned per session   |     |
|                  +--------------------+-----------------+     |
|                                       |                       |
|                                       v (UNIX socket)         |
|                  +--------------------------------------+     |
|                  |        convoyd  (daemon)             |     |
|                  |   - heartbeat / liveness checker     |     |
|                  |   - notification dispatcher          |     |
|                  |   - export writer                    |     |
|                  +--------------------+-----------------+     |
|                                       |                       |
|                                       v                       |
|                  +--------------------------------------+     |
|                  |    SQLite per project                |     |
|                  |    ~/.convoy/projects/<id>/state.db  |     |
|                  +--------------------------------------+     |
+--------------------------------------------------------------+
```

### 4.2 Process model

- **`convoyd`** — long-running daemon. Owns: liveness checks (PID probe every
  60s), expiry sweeps (locks past TTL), notification fan-out (writes wake
  pending `wait_for` subscribers), exports/ mirror generation. Communicates
  with MCP server via UNIX socket at `~/.convoy/daemon.sock`.

- **`convoy mcp`** — short-lived MCP stdio server. Spawned by Claude Code
  via `claude mcp add convoy -- convoy mcp`. One process per session. On
  start, registers the session by talking to `convoyd` over the socket.

- **`convoy hook <event>`** — invoked synchronously by Claude Code hooks
  (`SessionStart`, `PreToolUse`, `PostToolUse`, `Stop`). Writes a small
  payload to `convoyd` and exits.

- **`convoy <user-command>`** — the human-facing CLI (`list`, `status`, ...).
  Reads SQLite directly for read-only commands; talks to `convoyd` for
  mutating commands.

### 4.3 Why daemon + SQLite (not pure SQLite)

The daemon is needed for three things that SQLite alone cannot do:

1. **Push notifications** — `wait_for` must wake when a condition changes.
   SQLite has no built-in notify; without a daemon, MCP servers would have
   to busy-poll.
2. **Heartbeat sweeps** — detecting that a session's PID died requires a
   process actively probing. SQLite cannot do this on its own.
3. **TTL expiry** — file-locks past `expires_at` need someone to release
   them even if no one is reading.

Storage stays in SQLite (daemon never owns durable state) so a daemon crash
is recoverable: restart the daemon, no data lost.

### 4.4 Single binary, multiple subcommands

```
convoy daemon              # start convoyd in foreground
convoy mcp                 # stdio MCP server (Claude Code spawns this)
convoy hook <event>        # called by Claude Code hooks
convoy list                # user CLI: list projects
convoy status [project]    # user CLI: current state
convoy show <project>      # user CLI: print exports
convoy export <project>    # user CLI: dump portable state
convoy finish <project>    # user CLI: archive + stop accepting sessions
convoy forget <project>    # user CLI: delete everything for a project
convoy doctor              # user CLI: integrity checks
convoy gc                  # user CLI: garbage collect ended sessions
convoy setup               # one-time onboarding (writes hooks, etc.)
```

All subcommands ship in one Rust binary (`convoy`).

## 5. Storage Design

### 5.1 File tree

```
~/.convoy/
+-- config.toml                # global settings (log level, daemon port, rate limits)
+-- projects.toml              # registry: abs_path -> project_id
+-- daemon.sock                # UNIX socket (transient)
+-- daemon.pid                 # daemon pid (transient)
+-- daemon.log                 # rotated log (10 MB x 5)
|
+-- projects/
    +-- <project-id>/          # project_id = sha256(realpath(root))[:12]
        +-- meta.toml          # plain-text: path, created_at, last_active_at, status
        +-- state.db           # SQLite (durable)
        +-- state.db-wal       # SQLite WAL
        +-- state.db-shm       # SQLite shared-memory
        +-- exports/           # daemon-generated human-readable mirror
        |   +-- sessions.md
        |   +-- recent_mail.md
        |   +-- locks.md
        |   +-- timeline.md
        +-- archive/           # populated by `convoy finish`
            +-- 2026-05-11_session_<id>.json
```

**Design principles** (matching user constraints):
- Per-project structural isolation (`rm -rf projects/<id>/` = forget that project)
- Plain-text `meta.toml` so `cat` shows what's inside
- Auto-generated markdown mirror in `exports/` so users without SQL skills can inspect
- Archive-before-delete: `finish` archives, `forget` actually removes

### 5.2 `meta.toml` schema

```toml
project_path     = "/Users/foo/repo"
project_root_real = "/Users/foo/repo"      # symlink-resolved
git_common_dir   = "/Users/foo/repo/.git"  # set if a git repo (worktrees share this)
created_at       = "2026-05-11T10:00:00Z"
last_active_at   = "2026-05-11T14:30:00Z"
status           = "active"                 # "active" | "finished"
convoy_version   = "0.1.0"
schema_version   = 1
```

### 5.3 SQLite schema

```sql
CREATE TABLE schema_version (version INTEGER NOT NULL);

CREATE TABLE sessions (
  id              TEXT PRIMARY KEY,           -- uuid v4
  agent           TEXT NOT NULL,              -- 'claude-code' (M2: 'codex' | 'gemini')
  pid             INTEGER NOT NULL,
  branch          TEXT,
  worktree_path   TEXT,
  nickname        TEXT NOT NULL,
  started_at      INTEGER NOT NULL,           -- unix epoch seconds
  last_heartbeat  INTEGER NOT NULL,
  last_seen_alive INTEGER NOT NULL,           -- updated by daemon PID probe
  ended_at        INTEGER                     -- NULL = alive
);
CREATE INDEX idx_sessions_alive ON sessions(ended_at);

CREATE TABLE messages (
  id              TEXT PRIMARY KEY,           -- uuid v4
  from_session    TEXT NOT NULL,
  to_session      TEXT,                       -- NULL = broadcast
  kind            TEXT NOT NULL CHECK (kind IN
                    ('info','question','ack','request-yield',
                     'claim-notice','status-broadcast')),
  in_reply_to     TEXT,                       -- another message.id
  body            TEXT NOT NULL,
  created_at      INTEGER NOT NULL,
  read_at         INTEGER
);
CREATE INDEX idx_msg_inbox ON messages(to_session, read_at);
CREATE INDEX idx_msg_thread ON messages(in_reply_to);

CREATE TABLE file_locks (
  abs_path        TEXT PRIMARY KEY,           -- UNIQUE => no double-claim
  session_id      TEXT NOT NULL,
  reason          TEXT,
  claimed_at      INTEGER NOT NULL,
  expires_at      INTEGER NOT NULL            -- TTL; daemon auto-releases past this
);
CREATE INDEX idx_locks_session ON file_locks(session_id);
CREATE INDEX idx_locks_expiry ON file_locks(expires_at);

CREATE TABLE status_updates (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id      TEXT NOT NULL,
  summary         TEXT NOT NULL,              -- 1-2 lines, <= 500 chars
  created_at      INTEGER NOT NULL
);
CREATE INDEX idx_status_session ON status_updates(session_id, created_at DESC);

CREATE TABLE waits (                          -- pending wait_for subscriptions
  id              TEXT PRIMARY KEY,
  session_id      TEXT NOT NULL,
  condition_json  TEXT NOT NULL,              -- structured condition (see 7.4)
  hint            TEXT,
  created_at      INTEGER NOT NULL,
  expires_at      INTEGER NOT NULL,
  satisfied_at    INTEGER,                    -- NULL = still waiting
  outcome         TEXT                        -- 'satisfied' | 'timeout' | 'cancelled'
);
CREATE INDEX idx_waits_pending ON waits(session_id, satisfied_at);

CREATE TABLE events (                         -- append-only audit / timeline
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  ts              INTEGER NOT NULL,
  session_id      TEXT,                       -- nullable for daemon-originated events
  kind            TEXT NOT NULL,              -- 'register'|'heartbeat'|'claim'|'release'|...
  payload_json    TEXT
);
CREATE INDEX idx_events_ts ON events(ts);
```

WAL mode is enabled (`PRAGMA journal_mode=WAL`). Busy timeout is 5 seconds.

### 5.4 Human-readable mirror

Daemon regenerates `exports/*.md` every 10 seconds while any session is
active. Format example for `sessions.md`:

```markdown
# Sessions in /Users/foo/repo

Updated: 2026-05-11T14:32:01Z  (auto-generated, do not edit)

## Active (2)

### feat-auth  (alive, active 12s ago)
- id:        b3f4c2e1
- pid:       48217
- agent:     claude-code
- branch:    feature/auth-rewrite
- worktree:  /Users/foo/repo-auth
- started:   2026-05-11T13:50:11Z
- last status: "Refactoring login flow into auth/login.rs"

### refactor-config  (idle, active 4m ago)
- id:        9a7d2f08
- pid:       48311
- agent:     claude-code
- branch:    refactor/config
- worktree:  /Users/foo/repo
- started:   2026-05-11T14:01:55Z
- last status: "Waiting on lock: src/main.rs (held by feat-auth)"

## Ended in last 24h (1)

- crimson-otter  ended 2026-05-11T13:45:09Z  (graceful)
```

Users can `cat` this without ever touching SQLite.

### 5.5 Project identification

```
project_root  = first ancestor containing .git, else current working directory
git_common    = `git rev-parse --git-common-dir` if in a git repo
canonical_id  = sha256(realpath(git_common or project_root))[:12]
```

Critically, two git worktrees of the same repo share `git_common_dir`, so
they map to the **same** `project_id` and **the same `state.db`**. This is
exactly what we want: sibling worktrees should see each other's locks.

## 6. Session Lifecycle

### 6.1 Registration

Triggered by Claude Code's `SessionStart` hook calling `convoy hook session-start`.
The hook script:

1. Resolves `project_id` from `$CWD`
2. Reads `$CLAUDE_SESSION_ID` from environment (Claude Code provides this)
3. Sends `register` RPC to daemon containing pid, branch, worktree path
4. Daemon writes a row to `sessions` with `nickname = branch_name || random_animal()`
5. Daemon writes a `claim-notice`-style broadcast: `"<nickname> joined"`

Nickname auto-defaults but is changeable via `coord.rename(name)` MCP tool.

### 6.2 Identity

- `session_id`: uuid v4 (DB key; stable across renames)
- `nickname`: human-readable (default = branch name, fallback random adjective-animal)
- Display form in UI/messages: `nickname (#id[:6])` e.g. `feat-auth (#b3f4c2)`

### 6.3 Heartbeat

Two complementary signals:

- **`last_heartbeat`** updated by Claude Code's `PreToolUse` / `PostToolUse` /
  `UserPromptSubmit` hooks. Reflects model activity.
- **`last_seen_alive`** updated by daemon every 60s via `kill(pid, 0)`.
  Reflects whether the OS process exists.

UI shows:
- "active" if `now - last_heartbeat < 60s`
- "idle" if alive but inactive
- "dead" if PID probe fails

### 6.4 Deregistration

Three paths, in order of preference:

1. **Graceful** — `Stop` hook calls `convoy hook session-stop`. Daemon sets
   `ended_at`, releases all file_locks held by this session, marks pending
   waits as cancelled, broadcasts `"<nickname> left"`.

2. **Timeout** — Daemon's PID probe sees process gone. After
   `last_seen_alive` is older than 5 minutes AND `kill(pid, 0)` fails,
   treats the session as ended (same cleanup as graceful).

3. **TTL** — Even if the daemon is itself down, every lock has
   `expires_at`. Default lock TTL is 30 minutes. Any client reading the DB
   ignores expired locks.

### 6.5 Branch tracking

`PostToolUse` hook detects when the last tool was a Bash call matching
`git\s+(checkout|switch|worktree)` and re-reads `git rev-parse --abbrev-ref HEAD`,
then `update_branch` RPC to daemon.

## 7. Communication Protocol

### 7.1 MCP tool surface (exposed to the Claude Code model)

```
convoy.list_sessions(include_ended: bool = false)
    -> [{id, nickname, agent, branch, status, last_status_summary}]

convoy.send_message(to: str | None,
                    kind: "info"|"question"|"ack"|"request-yield"|"status-broadcast",
                    body: str,
                    in_reply_to: str | None = None)
    -> {message_id}
    # Note: 'claim-notice' is reserved; emitted only by claim_file, not callable here.

convoy.read_inbox(unread_only: bool = true, limit: int = 20)
    -> [{id, from_nickname, kind, body, created_at}]

convoy.mark_read(message_ids: list[str])
    -> {marked: int}

convoy.update_status(summary: str)        # 1-2 line progress
    -> {ok: true}

convoy.claim_file(abs_path: str, reason: str, ttl_sec: int = 1800)
    -> {claimed: true, expires_at: int}
      | {claimed: false, held_by: str, held_until: int}

convoy.release_file(abs_path: str)
    -> {released: true}

convoy.list_my_claims()
    -> [{abs_path, reason, expires_at}]

convoy.wait_for(condition: WaitCondition, timeout_sec: int = 600,
                hint: str | None = None)
    -> {wait_id, status: "waiting" | "already-satisfied"}
    # "already-satisfied" means condition was true at call time (e.g. lock was
    # already free). "waiting" means a row was created and a later hook
    # injection will deliver "satisfied" or "timeout" via the inbox-style
    # update channel (see 7.3).

convoy.cancel_wait(wait_id: str)
    -> {ok: true}

convoy.rename(nickname: str)
    -> {ok: true}
```

`WaitCondition` is one of:
- `{type: "lock_released", abs_path: str}`
- `{type: "session_ended", session_id: str}`
- `{type: "message_received", from: str | None, kind: str | None}`

### 7.2 Hook responsibilities

| Claude Code event | What `convoy hook` does |
|---|---|
| `SessionStart` | Register session; inject summary of other active sessions + unread inbox + active locks into context via stdout |
| `UserPromptSubmit` | Touch `last_heartbeat`; inject new unread messages and satisfied/expired waits |
| `PreToolUse` | Touch `last_heartbeat`; if tool is `Write`/`Edit`/`NotebookEdit`, lookup file path against `file_locks` table and surface a warning if held by another session |
| `PostToolUse` | Touch `last_heartbeat`; if tool was `Bash` matching git branch-change pattern, refresh branch |
| `Stop` / `SessionEnd` | Graceful deregister |

The `PreToolUse` lock check is **advisory only in M1** — it surfaces a
warning into the model's context but does not block the write. This avoids
trapping users behind broken locks while we tune behavior. (Hard blocking is
M2+ after we see real-world behavior.)

### 7.3 Auto-inject format

When a hook fires, anything sent to stdout becomes context for the next
turn. Example injection from `UserPromptSubmit`:

```
<convoy-update timestamp="2026-05-11T14:32:01Z">
  active peers:
    - feat-auth      (branch feature/auth-rewrite, active 12s ago)
      status: "Refactoring login flow into auth/login.rs"

  unread messages (2):
    [question] from feat-auth: "Are you done with config.yaml?"
    [info]     from feat-auth: "I'll need src/main.rs in ~10 min"

  your wait w_8a2f satisfied: lock on src/config.yaml released
</convoy-update>
```

If there is nothing to report, the hook outputs nothing (no noise).

### 7.4 Wait semantics — non-blocking polling

Convoy's `wait_for` is **not** a blocking call. The flow:

1. Model calls `convoy.wait_for({type:"lock_released", abs_path:"x.rs"}, 600)`
2. Daemon creates a row in `waits`, returns immediately with `{wait_id, status:"waiting"}`
3. Model sees `waiting`, does other useful work in subsequent turns
4. When the condition is met (another session releases `x.rs`), daemon flips
   `satisfied_at` and the next hook injection tells the model
5. Model can `cancel_wait` if it no longer needs the result

This trades immediacy for safety: a model that "wakes up" mid-turn cannot
exist in current Claude Code; this design accepts that and works with the
turn model rather than against it.

### 7.5 Rate limiting

Per-session, enforced by daemon:

- 20 outgoing messages per minute (rolling window)
- 5 broadcasts per minute
- 30 status_updates per hour
- 10 file claims per minute

Defaults configurable in `config.toml`. Exceeding returns `{error:"rate-limited"}`.

This is a **safety rail, not a feature** — two LLMs that get into a reply
loop must be cut off, not allowed to fill the DB.

## 8. CLI Surface

```
convoy setup
  Interactive one-time setup. Writes hooks into ~/.claude/settings.json
  (with diff preview), starts daemon, prints `claude mcp add` command.

convoy daemon [--foreground]
  Run the daemon. Without --foreground, daemonizes.

convoy mcp
  stdio MCP server. Not invoked by users directly.

convoy hook <event>
  Called by Claude Code hooks. Not invoked by users directly.

convoy list
  Show all known projects with active session counts.

convoy status [<project-path>]
  Show active sessions, locks, recent mail for one project (default: cwd).

convoy show <project-path> [--section sessions|mail|locks|timeline]
  Print one of the markdown mirror files.

convoy export <project-path> [--to <dir>] [--redacted]
  Dump portable JSON+markdown bundle.

convoy finish <project-path>
  Archive current state to archive/, set project status to "finished",
  refuse new session registrations. Reversible by `convoy reopen`.

convoy reopen <project-path>
  Undo `finish`.

convoy forget <project-path> --yes
  Delete entire projects/<id>/ folder. Requires explicit --yes.

convoy doctor
  Check: schema_version current, no stale daemon.pid, no orphan locks
  past TTL, projects.toml entries match folders on disk.

convoy gc [--older-than 30d]
  Delete rows where ended_at < threshold.

convoy version
```

## 9. Error Handling & Failure Modes

| Scenario | Behavior |
|---|---|
| Daemon not running when MCP server starts | MCP server auto-spawns `convoy daemon` and retries socket connect for 5s; if still failing, returns clear error to the model on every tool call |
| SQLite locked (concurrent writer) | Retry with backoff up to 5s (sqlite busy_timeout) |
| Session's PID reused before daemon notices | `register` checks `last_seen_alive`; if a session row for that PID exists but `pid` no longer maps to it (start_time differs), the row is reaped first |
| Hook script fails (non-zero exit) | Logged but does not break the Claude Code turn (hook stderr is captured separately) |
| Disk full | Daemon logs ERROR and serves read-only operations; writes fail with clear error |
| `state.db` corrupted | `convoy doctor` flags; `convoy export` still attempts dump; user can `convoy forget` and restart |
| Two sessions race to claim same file | SQLite `UNIQUE PRIMARY KEY` ensures exactly one wins; the loser sees `{claimed:false, held_by:...}` |
| User deletes `~/.convoy/projects/<id>/` manually | Next `convoy list` rebuilds `projects.toml` index; in-flight sessions get clean errors |

## 10. Testing Strategy (TDD)

The architecture is built for TDD. Each module has a clearly-bounded
contract and can be tested in isolation.

### 10.1 Test layers

```
+----------------------------+
|   End-to-end tests         |  spawn convoyd + two mock MCP clients,
|                            |  run full claim/yield/release flow
+----------------------------+
|   Integration tests        |  one daemon + one MCP client per test,
|                            |  real SQLite (temp dir), real UNIX socket
+----------------------------+
|   Unit tests               |  pure functions: project_id derivation,
|                            |  rate limiter, schema migrations,
|                            |  hook payload parsing, wait condition matcher
+----------------------------+
```

### 10.2 TDD-first crates

The Rust workspace will be split so each crate has a precise testable surface:

```
crates/
+-- convoy-core      # domain types, no I/O (Session, Message, Lock, WaitCondition)
+-- convoy-store     # SQLite-backed repository; trait-based for in-memory test impl
+-- convoy-daemon    # daemon binary; depends on convoy-store
+-- convoy-mcp       # MCP server binary; depends on convoy-core only (talks to daemon over socket)
+-- convoy-hook      # hook subcommand; depends on convoy-core
+-- convoy-cli       # human CLI subcommands
+-- convoy-bin       # the top-level `convoy` binary that dispatches subcommands
```

`convoy-core` has zero I/O dependencies, so every domain rule (rate-limit
counter, wait-condition matcher, message-routing logic, lock-expiry check)
is a pure-function unit test.

`convoy-store` has a `Store` trait. Two implementations:
- `SqliteStore` — production
- `MemoryStore` — for daemon-level integration tests where we want to
  exercise daemon logic without SQLite touch

### 10.3 Sample TDD red/green/refactor cycle

Example: implementing `claim_file`.

1. **Red** — write `claim_file_succeeds_on_unheld_path` against the
   `MemoryStore`. Compile error: trait method does not exist.
2. **Green minimum** — add `Store::claim_file` returning `Result<Claim>`,
   in-memory impl returns `Ok`. Test passes.
3. **Red** — write `claim_file_fails_when_already_held`. Fails.
4. **Green** — implement conflict check in `MemoryStore`. Passes.
5. **Red** — write `claim_file_succeeds_after_ttl_expiry`. Fails.
6. **Green** — implement TTL logic.
7. **Refactor** — extract `Lock::is_expired(now)` to `convoy-core`, both
   stores delegate.
8. **Red** — write the same three tests against `SqliteStore`. Run on real
   SQLite in a temp dir.
9. **Green** — implement `SqliteStore::claim_file` with the SQL.

Each level (core → store → daemon → e2e) gets its own test file.

### 10.4 Test infrastructure

- `tempfile` for per-test SQLite paths
- `tokio::test` for daemon integration tests
- A `TestHarness` builder spawning a real `convoyd` on a temp socket
- Snapshot tests (`insta`) for `exports/*.md` formatting
- Property tests (`proptest`) for rate-limiter invariants and project_id
  determinism

### 10.5 Coverage gates

- `convoy-core` >= 95% line coverage (it's pure)
- `convoy-store` >= 90%
- Daemon happy-path + every error branch in section 9 has an integration test

## 11. Security & Privacy

- Daemon binds **only** UNIX socket at `~/.convoy/daemon.sock` (0600 perms).
  No TCP listener in M1.
- `projects.toml` and `state.db` files chmod 600.
- `meta.toml` records the absolute project path; `convoy export --redacted`
  replaces paths with `<project-root>/...` for sharing in bug reports.
- No telemetry. No outbound network calls.
- M1 trusts every local process running as the same UID. Per-session
  authentication is deferred to M2 (when remote actors / containers join).

## 13. Risks & Open Questions

| Risk | Mitigation |
|---|---|
| Claude Code hook surface may change between versions | Pin minimum supported Claude Code version; `convoy doctor` warns on hook drift |
| MCP stdio cold-start adds latency to every Claude session | Daemon is hot; only `convoy mcp` startup matters (Rust binary, ~5ms) |
| Rate limits could be bypassed if model batches into one body | Daemon enforces by `from_session` and timestamp, not content shape |
| User deletes `~/.convoy` while a session is live | Session's next hook call fails loudly with "convoy state lost; run `convoy setup`" |
| Two daemons start (race on `daemon.pid`) | `flock(daemon.pid)` enforces single instance |
| Worktree on a different filesystem than `.git` | Hash of `git rev-parse --git-common-dir` still gives the same id |

### Open questions to resolve in implementation plan

1. Exact Rust MCP SDK to use: `rmcp` vs `rust-mcp-sdk` vs custom. Decide
   after a 30-min spike on each.
2. Daemon log rotation crate (`tracing-appender` likely).
3. Hook installer: do we modify `~/.claude/settings.json` directly, or
   provide a snippet for the user to paste? `convoy setup` should diff
   before writing.

## 15. Acceptance Criteria for M1

M1 ships when **all** of the following are demonstrably true with two
Claude Code sessions on one machine:

1. Open two Claude Code sessions in different terminals on the same repo
   (one in a worktree). Both auto-register; each can `convoy.list_sessions`
   and see the other.
2. Session A can `convoy.claim_file("src/main.rs", "refactoring login")`.
   Session B's next attempt to claim the same file returns
   `{claimed:false, held_by:"A"}`.
3. Session A `convoy.update_status("done with login")`. Session B's next
   turn includes A's status in its injected context.
4. Session A `convoy.send_message(to="B", kind="question", body="...")`.
   Session B's next turn shows the question.
5. Session B `convoy.wait_for({type:"lock_released", abs_path:"src/main.rs"})`.
   Session A `convoy.release_file("src/main.rs")`. Session B's next turn
   shows the wait satisfied.
6. Kill Session A (SIGKILL, no graceful Stop). Within 5 minutes,
   daemon marks A ended and releases A's locks; Session B sees this.
7. `convoy status` from the terminal shows the current state of both.
8. `convoy finish <project>` archives state and `convoy forget <project>
   --yes` removes everything.
9. `convoy doctor` runs clean.
10. CI test suite passes on macOS and Linux.
